# Spec v03.1: The comparison across build tools

This spec adds to [v01.1](v01.1-benchmark-protocol.md) and
[v02.1](v02.1-fairness-and-rust-value.md); everything there still holds.
Section numbers name the section they extend. Like them it is accepted before
the run that uses it, and a report names the revision it ran.

## Subjects (extends §Subjects)

Two groups join `main`, `default-config` and `postcss`. Each has its own
baseline, so every number in a group is read against that group's baseline.

| Group | Subject | Runtime | Packages | Entry |
| --- | --- | --- | --- | --- |
| `rsbuild` | `rsbuild-baseline` | Node | `@rsbuild/core` | the modules only |
| `rsbuild` | `teacss-ts-rsbuild`, `teacss-rs-rsbuild` | Node | `@teacss/rsbuild` with `@rsbuild/core` | `index.css`: `@presets "standard"; @source "./src/**/*.js"; @teacss;`, imported from the JavaScript entry |
| `rsbuild` | `tailwind-v4-rsbuild` | Node | `@rsbuild/plugin-tailwindcss` with `tailwindcss` | `src/index.css`: `@import "tailwindcss" source(none); @source "./**/*.js";`, imported from the JavaScript entry |
| `bun` | `bun-baseline` | Bun | none | the modules only |
| `bun` | `teacss-ts-bun`, `teacss-rs-bun` | Bun | `@teacss/bun` | the JavaScript entry imports `virtual:teacss.css`; `pluginTeacss("<root>/index.css")` with the same `index.css` as above |
| `bun` | `tailwind-v4-bun` | Bun | `bun-plugin-tailwind` with `tailwindcss` | `src/index.css` as above, imported from the JavaScript entry |

Each tool runs the way its documentation says. `@teacss/rsbuild` optimizes with
lightningcss in production and `@rsbuild/plugin-tailwindcss` is built on
`@tailwindcss/webpack` with Tailwind's own lightningcss optimization in
production; neither goes through PostCSS. The Bun plugins hand their CSS to
Bun's bundler, which parses and prints it, with `minify: true` for every Bun
subject. The TeaCSS Rsbuild and Bun plugins take no engine option, so the
engine is chosen by `TEACSS_ENGINE` with `TEACSS_ENGINE_STRICT=1`, as the
PostCSS subjects already do.

The registry records each subject's runtime. A Node subject runs under the
pinned Node as before. A Bun subject runs under the Bun the repository pins in
`package.json` `packageManager`, and the environment record already names that
version. The `bun` group therefore compares runtimes as well as CSS tools, and
every table of that group says so in its caption.

## Tiers (extends §Tiers)

Both groups run the `build` tier only. The `engine` tier is tool-independent
and already measured; the `dev` tier for these tools is a later proposal.

| Subject | Build |
| --- | --- |
| `rsbuild-*` | `createRsbuild({ cwd, rsbuildConfig })` with `source.entry = { index: "./src/index.js" }`, production mode, `output.filenameHash: false`, then `build()`; the CSS is every `dist/static/css/*.css` concatenated |
| `bun-*` | `Bun.build({ entrypoints: ["src/index.js"], outdir, plugins, minify: true })`; the CSS is every output whose path ends in `.css` concatenated |

As in v01.1, one build per process, and the process reports its own resource
usage. The project files are the corpus project of §Corpus with the entries
above; the modules carry no header, since neither plugin needs one.

## Native modules (extends §Run protocol step 5)

A Node subject reports its loaded `.node` files from `process.report` as
before. Bun's `process.report` lists no addons, so a Bun subject wraps
`process.dlopen` before any tool code is imported and reports the file names
passed to it. The expectations per subject are the same as in `main`: a Rust
TeaCSS subject must have loaded `teacss-engine`, a TypeScript one must not,
and no TeaCSS subject may have loaded `tailwindcss-oxide`; the Rsbuild
subjects must have loaded the Rspack binding.

Revision 2 (2026-10-22, before any run) records the prototype: under Bun 1.4.3
the `process.dlopen` wrapper sees `teacss-engine` for the Rust TeaCSS subject,
nothing for the TypeScript one and `tailwindcss-oxide` for Tailwind, so no
substitution is needed. Both runtimes report `resourceUsage().maxRSS` in
kilobytes, and Bun writes CPU profiles the limiter table reads. Strong
equivalence pairs each `teacss-ts…` subject with its `teacss-rs…` twin in
every group, the existing groups included. A run refuses a Bun other than the
one `packageManager` pins unless `--allow-bun-mismatch` is passed.

## Equivalence (extends §Equivalence)

The structural check accepts a logical shorthand's two longhands as the
expected property: `padding-inline`, `margin-inline`, `inset-inline`,
`padding-block`, `margin-block` and `inset-block` each match when both of their
`-start` and `-end` longhands are declared with the expected conditions. Bun's
bundler expands some of these shorthands when it prints the stylesheet (76 of
5 000 Tailwind cases at 5 000 x 30 in the pre-experiment, none for TeaCSS); the
rule applies to every subject and the verification summary counts the cases
matched through longhands.

Strong equivalence (byte-identical output between `teacss-ts-*` and
`teacss-rs-*`) is checked per group, as in `main`.

## Report (extends §Report)

- The result tables are per group, as v02.1 already does for
  `default-config` and `postcss`; each `bun` table's caption states that the
  group runs in the Bun runtime.
- A **Build tools** table at the largest cell: one row per group with the
  baseline's median, then for each CSS tool its median and its delta over that
  baseline. The baseline column is labelled as comparing bundlers and
  runtimes, not CSS tools; the deltas are the comparison.
- The README summary gains one takeaway per tool: what TeaCSS and Tailwind
  each add to a build on that tool, and which is smaller.
- The record carries `v03Revision`, every subject's runtime and group, and
  the Bun version the Bun subjects ran under. Reports refuse to compare records
  of different revisions, as before.

## Acceptance and verification

| Requirement | Check |
| --- | --- |
| Every subject builds the corpus | `bench verify --group rsbuild,bun` passes at 5 000 x 30 and 20 000 x 300 |
| Same work | the structural check passes for every subject; the longhand rule's use is counted and reported |
| ts equals rs | byte-identical output within `rsbuild` and within `bun` |
| Right runtime | a Bun subject's record names the Bun version; a Node subject's the pinned Node |
| Right binaries | native expectations per subject hold on every response, or the report names the substitution for Bun |
| Baselines | each group's baseline builds the same project with no CSS tool |
| Report | per-group tables, the Build tools table and the README takeaways render from a record with all five groups, and the first two reports regenerate byte for byte |
