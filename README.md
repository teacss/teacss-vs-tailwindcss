# teacss-vs-tailwindcss

A reproducible performance comparison of three atomic CSS engines on the same
machine, the same paired corpus and the same build pipelines (Vite, PostCSS,
Rsbuild and Bun): the TeaCSS TypeScript engine (`@teacss/core` with
`@teacss/vite-ts`), the TeaCSS Rust engine (`@teacss/engine` with `@teacss/vite`
and the other teacss-rs integrations) and Tailwind CSS v4 (Oxide). Since 0.10
the two TeaCSS engines are separate ecosystems that share no package
([ADR-0005](notes/adrs/ADR-0005-two-teacss-ecosystems.md)).

## Status

The subjects now pin TeaCSS 0.10 under spec revision 10: teacss-rs 0.10.5 and
teacss-ts 0.10.5, two ecosystems that share no package, on Node 26
([ADR-0005](notes/adrs/ADR-0005-two-teacss-ecosystems.md)). TeaCSS 0.10 has no
published run yet, so the block below still shows 0.9.3, and its numbers do
not carry over to 0.10.

Seven published runs; the latest (2026-10-25) measures TeaCSS 0.9.3 across
Vite, PostCSS, Rsbuild and Bun under spec revision 8. Revisions 5 to 8 made
each subject process match what a CLI user gets: the compile cache and the
`NODE_ENV` the `vite` and `rsbuild` CLIs set, only the packages the task uses,
and a run that is discarded when the machine gets busy mid-run. Build, dev and
cold-engine numbers are therefore not comparable with earlier runs. Revision 6
also corrected a bias that made every earlier TypeScript-engine dev number too
fast. The CSS is byte-for-byte the same as 0.9.0
([what changed in 0.9.2 and 0.9.3](notes/articles/teacss-0.9.3.md)). Two
articles explain the 0.9.0 round in plain language:
[the TypeScript engine against the Rust engine](notes/articles/teacss-0.9.0-ts-vs-rust.md)
and [TeaCSS against Tailwind CSS v4](notes/articles/teacss-0.9.0-vs-tailwind-v4.md).
Fixes merged but not yet published are measured separately in an unreleased
lane that never enters the block below
([optimization cards](notes/knowledge/optimization-cards-2026-10-24.md)).
The block below is generated by
`bun run bench:report <results.json> --readme README.md` after every run and
is written for developers who want the answer without reading the full report.

### Results from 2026-10-25

**Generating the CSS for 20,000 classes** (median of 30 runs)

| | Time |
| --- | --- |
| TeaCSS (Rust engine) | 52 ms |
| Tailwind CSS v4 | 232 ms (4.5× slower) |
| TeaCSS (TypeScript engine) | 495 ms (9.6× slower) |

**Adding new classes to an engine** that already holds those 20,000 (median of 30 runs)

| | +10 classes | +100 classes |
| --- | --- | --- |
| TeaCSS (Rust engine) | 18 ms | 19 ms |
| TeaCSS (TypeScript engine) | 112 ms (6.1× slower) | 117 ms (6.3× slower) |
| Tailwind CSS v4 | 140 ms (7.7× slower) | 145 ms (7.8× slower) |

**Saving a new file in the Vite dev server** with 20,000 classes already in 300 files, until the page's stylesheet has the new classes (median of 30 runs)

| | +10 classes | +100 classes |
| --- | --- | --- |
| TeaCSS (Rust engine) | 77 ms | 73 ms |
| TeaCSS (TypeScript engine) | 311 ms (4.1× slower) | 321 ms (4.4× slower) |
| Tailwind CSS v4 | 324 ms (4.2× slower) | 311 ms (4.2× slower) |

**Building a Vite project with those classes in 300 files** (median of 30 runs; the project builds in 185 ms with no CSS tool)

| | Build | of which CSS |
| --- | --- | --- |
| TeaCSS (Rust engine) | 405 ms | 220 ms |
| Tailwind CSS v4 | 759 ms (1.9× slower) | 574 ms |
| TeaCSS (TypeScript engine) | 1.02 s (2.5× slower) | 831 ms |

**What the Rust engine changes for TeaCSS**

| | TypeScript engine | Rust engine |
| --- | --- | --- |
| Generate the CSS (warm process) | 495 ms | 52 ms (9.6× faster) |
| Add 10 classes to a running engine | 112 ms | 18 ms (6.1× faster) |
| Dev server: save a file with 10 new classes | 311 ms | 77 ms (4.1× faster) |
| Vite production build | 1.02 s | 405 ms (2.5× faster) |
| Resident memory after generating | 748.1 MB | 381.2 MB (2.0× less) |
| Same CSS output | | byte-identical in every measured case |

**In short**

- TeaCSS (Rust engine) is fastest both at generating the CSS and at finishing the build.
- Generating the CSS is only part of the build's CSS cost: 24 % for TeaCSS (Rust engine). The rest is the build plugin, so a faster engine does not by itself give a faster build.
- For the same classes, Tailwind CSS v4 emits 2.6× the CSS of TeaCSS: 30,010 rules against 4,832. Part of its build time goes to producing that extra output.
- The price of the Rust engine is a native file of 8.4 MB per platform (8 platform packages), loaded in 1.2 ms. It served 6 of the 6 example configurations it was given.
- Every tool was given the same classes, and before anything was timed each tool's output was checked against them; every timed call that added classes was checked for those classes. The tools emit different colour and size values by design, so this is the time to a correct stylesheet, not to identical bytes.
- vite 8.3.4, @teacss/core 0.9.3, @teacss/engine 0.9.3, tailwindcss 4.3.3; one Apple M2 Max, Node v24.14.1. Milliseconds will differ on your machine; the ratios carry over.
- With each tool's out-of-the-box entry instead of the tuned one, the build takes 0.98× as long for TeaCSS (Rust engine), 0.99× as long for TeaCSS (TypeScript engine) and 1.00× as long for Tailwind CSS v4, so the comparison does not hinge on one tool's configuration.
- On other build tools: with Rsbuild, TeaCSS (Rust engine) adds 304 ms to the build and Tailwind CSS v4 adds 992 ms, so TeaCSS (Rust engine) adds less; with Bun (Bun runtime), TeaCSS (Rust engine) adds 153 ms to the build and Tailwind CSS v4 adds 340 ms, so TeaCSS (Rust engine) adds less. The Build tools section of the full report sets them beside Vite.

## Layout

The repository follows Billgo's standard architecture for a Node.js tool:
four layers, one dependency direction, one process per native runtime.

| Unit | Layer | Holds |
| --- | --- | --- |
| `apps/bench` | shell | `main.ts` (the orchestrator) and `subject.ts` (one measured subject per process) |
| `packages/benchmark` | product | measure, verify, report, profile and environment features; the shared corpus model and CSS helpers; the composition root; the process contract; persistence |
| `packages/infrastructure` | foundation | config, logging, clock, processes, workspace, the `SubjectClient` interface and its fakes |
| `packages/subject-*` | isolation | one measured runtime each behind the `SubjectClient` interface |
| `results/` | data | raw samples committed with each report |
| `notes/` | documentation | proposals, specs, plans, ADRs, knowledge, reports, articles |

A shell depends on exactly one product. The product depends on the foundation
and the isolation units, and only its composition root picks an
implementation. An isolation unit depends on the foundation alone. The
foundation depends on nothing in the workspace. `scripts/check-layout.ts` and
`scripts/check-dependencies.ts` fail the build on any deviation.

## Develop

Bun installs the workspace; Node 26 runs the TypeScript sources directly, so
there is no build step. The teacss-rs packages need Node 26 or later.

```sh
bun install
bun run check
```

`bun run check` runs Biome, the per-package type checks, the tests and both
structure checks. Each script can run on its own: `bun run lint:check`,
`bun run typecheck`, `bun run test`, `bun run check:layout`,
`bun run check:dependencies`.

## Measure

```sh
bun run bench:verify --utilities 5000 --files 30   # equivalence checks on one corpus
bun run bench:cases                                  # the behaviours the 0.10 upgrade guide names
bun run bench                                        # the full matrix, 30 samples per cell, into results/
bun run bench:ts-tailwind                            # the same without teacss-rs
bun run bench:report results/<file>.json --readme README.md   # report, JSON summary, and the README block
```

`bun run bench` measures each tool twice: with the tuned production entry and
with the entry its setup guide gives (`--group main,default-config`, the
default). The other groups run on request, all of them at once with
`--group main,default-config,postcss,rsbuild,bun,cli`: the PostCSS integrations
(`postcss`), Rsbuild and Bun (`rsbuild`, `bun`), and the two TeaCSS command
lines, `teacss-cli` and `teacss` (`cli`). teacss-ts publishes no PostCSS,
Rsbuild or Bun integration since 0.10, so those groups have one TeaCSS subject,
on the Rust engine.

Verification compares the two TeaCSS engines byte for byte, the two command
lines byte for byte with font URLs reduced to their digest, and the two Vite
plugins byte for byte. `@teacss/vite` 0.10.4 let its sheet skip Vite's CSS
pipeline, so revision 9 compared the plugins class by class; 0.10.5 fixes it,
and revision 10 restores the byte check. Every build
is also checked with another stylesheet imported ahead of the tool's own,
which `@teacss/vite` 0.10.3 failed under Vite 8.

To check that the generated corpus is not cherry-picked, run the same matrix on
classes taken from real Tailwind projects. List checked-out projects in a JSON
file, `[{ "name": "…", "dir": "path/to/src" }]`, then:

```sh
bun run bench:corpus --community projects.json     # coverage: how many of their utilities translate
bun run bench --community projects.json --out results
bun run bench:report results/<generated>.json --beside results/<community>.json --readme README.md
```

The `bench` GitHub workflow runs the same matrix on a Linux runner and uploads
its record as an artifact. Download it and attach it as a cross-check; the
report refuses records that ran a different spec revision or corpus:

```sh
bun run bench:report results/<local>.json --cross <ci-record>.json --readme README.md
```

To measure unreleased TeaCSS builds, link a built teacss-ts checkout
(`@teacss/core`, `@teacss/vite-ts`, `@teacss/preset-standard`), or a built
teacss-rs engine (`npm run build && npm run build:ts` in its `packages/engine`)
under the published TeaCSS packages. One link at a time:

```sh
bun run bench:link link --ts ../teacss-ts   # bench:link status shows where each package resolves
bun run bench:link link --rs ../teacss-rs   # every @teacss/engine the subjects reach, published packages otherwise
bun run bench:link unlink
```

A report from a linked run says so on its first line and is not for
publication. `bun run bench` refuses to start when the one-minute load exceeds 20 % of the
logical cores; `--allow-busy` records the run anyway and the report says so.
`node apps/bench/src/main.ts --help` lists every option. Bun is the package
manager; Node 26 runs the harness and every measured process, because that is the runtime a Vite build uses by default
([ADR-0003](notes/adrs/ADR-0003-published-packages.md)).
