# Spec v02.1: Fairness and the value of Rust

This spec adds to [v01.1](v01.1-benchmark-protocol.md); everything there still
holds. Section numbers below name the v01.1 section they extend. Like v01.1 it
is accepted before the run that uses it, and a report names the revision it ran.

## Tiers (extends §Tiers)

### `engine/incremental`

A warm process (three untimed full generations as in `engine/warm`) holds one
generator or compiler that has already produced the full corpus. Timed call *i*
asks for the full corpus plus every group of K new candidates so far (groups 1
to *i*), and the output must contain every new selector of group *i*. The
groups accumulate because Tailwind's compiler keeps every candidate it has
seen; asking TeaCSS for the same cumulative set gives both tools the same work,
as a dev server that keeps adding classes would. K is 10 and 100; each is its own
scenario (`engine/incremental-10`, `engine/incremental-100`). Ten timed calls
per process, each with a fresh set of K new candidates drawn from the pair
space outside the corpus; three processes give thirty samples.

| Subject | Timed call |
| --- | --- |
| `teacss-ts`, `teacss-rs` | the same generator's `generate(fullSet ∪ new)` |
| `tailwind-v4` | the same compiler's `build([...full, ...new])` |

Both tools keep what they generated before, so this is the cost of the next
change, not of a rebuild.

### `dev`: development-server update

The build-tier project is served by Vite's development server
(`createServer` with the subject's plugin, then `listen`). The orchestrator
fetches the stylesheet once so the first generation is done, then writes one
new module with K new classes, adds its import to the entry module, and polls
the stylesheet every 5 ms until every new selector is present. One sample is
the time from the write to the first stylesheet that contains all K selectors,
measured in the subject process. K is 10 and 100. Thirty samples per subject
and cell, each sample a fresh new module; the server stays up for a cell and a
fresh server starts for each cell. The polling adds at most 5 ms to every
subject equally, and the report says so.

The stylesheet URL is the subject's own: `virtual:teacss.css` for TeaCSS and
the CSS entry for Tailwind, both as Vite serves them. The `vite-baseline`
subject has no dev tier.

## Measurements (extends §Run protocol step 4)

Every engine-tier sample records, from inside the subject process around the
timed call: CPU time (`process.cpuUsage()` delta, user and system), resident
set size after the call (`process.memoryUsage().rss`), heap used after the
call (`heapUsed`), and the output's rule and declaration counts (parsed with
css-tree). Build-tier samples already carry CPU and peak RSS; they gain the
rule and declaration counts. A GC share comes from the profiling pass: the
`(garbage collector)` frame's self time over the profile total.

## Report (extends §Report)

Two tables join the report and the README block:

**The value of Rust**, `teacss-rs` against `teacss-ts` at the largest cell:
warm generation, incremental-10, incremental-100, dev-10, build; CPU time;
peak RSS; heap after generation; GC share; IQR as a share of the median; and
the number of cases with byte-identical output. Each row carries the ratio.

**The price of Rust**, for every subject that ships a native binary: the
`.node` file size for the running platform and the number of platform packages
the tool publishes (its `optionalDependencies`); the time to load that file in
a fresh process that has imported no tool code (`require` of the absolute path,
five processes, checked against the process's loaded shared objects before and
after); `bun install` of the tool's exact package set into an empty directory
with an empty cache, with the installed size; and how many TeaCSS entry
stylesheets the Rust engine can serve, judged by the engine facade's own
`translateConfig`, with each refusal's reason.

Revision 7 (2026-11-03) follows TeaCSS 0.10, where the TypeScript and Rust
engines became two ecosystems with their own packages (v01.1 revision 9):

- **The value of Rust** compares teacss-rs 0.10.4 with teacss-ts 0.10.3: each
  side's engine and its own Vite plugin. The engine rows compare the same
  bytes. The dev and build rows compare two pipelines, since `@teacss/vite-ts`
  runs the sheet through Lightning CSS and `@teacss/vite` does not, so the
  byte-identical row counts the engine groups as identical and the build and
  dev groups as differing.
- **The price of Rust** judges each entry stylesheet with `createProject` from
  `@teacss/engine`; the facade's `translateConfig` no longer exists. An entry
  the engine refuses has no fallback: it runs only on teacss-ts.
- **The PostCSS round** has two subjects, `teacss-rs-postcss` and
  `tailwind-v4-postcss`: teacss-ts publishes no PostCSS integration since
  0.10.

Dev and build samples of revisions 6 and 7 are not comparable.

Revision 6 (2026-10-25) runs the dev-tier subject processes with
`NODE_ENV=development`, which the `vite` CLI sets before it loads a config, as
v01.1 revision 6 describes. Dev-tier samples of revisions 5 and 6 are not
comparable.

Revision 5 (2026-10-24) runs the dev-tier subject processes with Node's compile
cache, as v01.1 revision 5 does for builds: the `vite` CLI enables it before it
starts the server. Dev-tier samples of revisions 4 and 5 are not comparable.

Revision 4 (2026-10-22) corrects where the dev-tier clock stops. A sample ends
when the first stylesheet response that contains every new selector is
received, as this section already said; the implementation had stopped it after
reading that response, so each sample carried the read's cost, about 10 ms to
50 ms at 20 000 utilities and more for the larger stylesheet. A polled response
whose text equals the last one is no longer read, which keeps the polls off the
server's thread while it works. Dev-tier samples of revisions 3 and 4 are not
comparable.

Revision 3 (2026-10-22, before any run used revision 2) follows an independent
review: incremental calls accumulate their groups for every tool (they had
asked TeaCSS for the corpus plus one group while Tailwind's compiler emitted all
groups so far); a class counts as present only when it ends at a selector
boundary (`.p-1` no longer matches inside `.p-10`); `bench run` runs the
equivalence checks on every corpus before timing anything and checks every
response's native modules; records carry this spec's revision, and reports
refuse to compare records of different revisions.

Revision 2 (2026-10-22) records two findings from implementing this table.
Since `@teacss/vite` 0.9.0-alpha.1 depends on `@teacss/engine` directly, an
install "without the engine" no longer exists, so the install row compares the
two tools' package sets instead. Importing a tool's package to time its binding
measured Tailwind's binding after the subject module had already loaded it
(0.3 ms against 2.7 ms), so the load is timed on the `.node` file alone.

**Work produced**, every subject at the largest cell: bytes, gzip bytes, rules,
declarations, and milliseconds per 100 KB. The report states that the last
column is context, not a ranking.

The report opens with the method's commit hash and the verification summary
(cases checked, differences found, runs invalidated) before the verdict.

## Corpus (extends §Corpus)

A second corpus, `community`, is built from public Tailwind projects:

1. The owner names the repositories. The rule for naming them: a public
   repository that uses Tailwind CSS v4 in production markup, not a Tailwind
   plugin or a component library's test fixtures, and not maintained by the
   TeaCSS authors.
2. Candidates are extracted with `@tailwindcss/oxide`'s `Scanner` over each
   repository's source directories, deduplicated, and kept only when the pair
   table can translate them to TeaCSS. The report gives the coverage: kept
   candidates over extracted ones, and the ten most frequent untranslated
   prefixes.
3. The kept candidates form the corpus in the extracted frequency order,
   truncated to the cell's utility count, spread over files like the generated
   corpus. Its hash and the repository list with commit hashes go in the record.

Both corpora run; the report shows the generated corpus first and the
community corpus beside it with the same tables.

## Configurations (extends §Subjects)

Each subject runs under two configurations:

| Configuration | TeaCSS | Tailwind v4 |
| --- | --- | --- |
| `default` | `@presets "standard"; @teacss;` with no `@source` (the plugin's own discovery) | `@import "tailwindcss";` (automatic source detection) |
| `production` | as v01.1 | as v01.1 (`source(none)` plus `@source "./**/*.js"`) |

The record names the configuration of every sample; the report shows both
side by side. A separate round runs the PostCSS integrations
(`@teacss/postcss`, `@tailwindcss/postcss`) through Vite's PostCSS pipeline
under the `production` configuration only, as subjects `teacss-rs-postcss`
and `tailwind-v4-postcss`. Revision 7 dropped `teacss-ts-postcss`, whose
package teacss-ts no longer publishes.

## Cross-check (extends §Environment record)

The CI workflow's run on `ubuntu-latest` is a cross-check: its report is
attached to the published report as a second environment, with the same
tables, and the verdict section states where the two machines agree on the
ranking and where they do not. CI numbers are never the headline.

## Acceptance and verification

| Requirement | Check |
| --- | --- |
| Incremental output is complete | every new selector present in the timed call's output, else the sample is invalid |
| Dev update is real | the polled stylesheet contains all K selectors; a timeout of 30 s invalidates the run |
| Resource numbers are per call | unit test with a fake subject: cpu and heap fields change between calls |
| Value and price tables | render from a synthetic record; the price table's sizes come from the installed packages, not from the registry |
| Community corpus | coverage and the untranslated prefixes printed; translation round-trips: translating back gives the original candidate |
| Two configurations | every sample names its configuration; a run missing one is reported as a subset |
| CI cross-check | the attached CI report ran the same spec revision and corpus hash |
