# Spec v01.1: Benchmark protocol

This document is the pre-registered method. It is accepted and committed
before the first published run. A published report follows the revision it
names; a deviation is recorded in the report, never by editing this file to
fit a result. A change bumps `spec-revision`.

## Outcome and scope

A reader outside TeaCSS can clone this repository, run one command and get
the same comparison, on their machine, of four subjects across two tiers and
a scale matrix, with every number traceable to raw samples and every subject
proven to have done the same work.

Excluded: the development-server incremental tier (second phase), Tailwind
v3, UnoCSS, teacss-zig, and a report website.

## Subjects

| Id | Packages (exact) | Engine switch | Native modules that must be loaded |
| --- | --- | --- | --- |
| `vite-baseline` | `vite` 8.3.4 | none | none |
| `teacss-ts` | `vite` 8.3.4, `@teacss/vite` 0.8.5, `@teacss/core` 0.8.5, `@teacss/preset-standard` 0.8.5 | `engine: "ts"` in the config (an explicit `"ts"` wins over the environment) | none; `@teacss/engine` is installed but never loaded |
| `teacss-rs` | the `teacss-ts` set plus `@teacss/engine` 0.8.5-alpha.3 and its platform package | `engine: "rust"` and `TEACSS_ENGINE_STRICT=1`, so a configuration Rust cannot serve throws instead of falling back | `teacss-engine.<platform>.node` |
| `tailwind-v4` | `vite` 8.3.4, `tailwindcss` 4.3.3, `@tailwindcss/vite` 4.3.3, `@tailwindcss/node` 4.3.3, `@tailwindcss/oxide` 4.3.3 | none | `tailwindcss-oxide.<platform>.node`; `lightningcss.<platform>.node` is loaded by both Tailwind and TeaCSS |

Every subject runs with its documented production configuration and the
packages as published on npm, installed with Bun from the committed `bun.lock`
([ADR-0004](../adrs/ADR-0004-bun-package-manager.md)); Node 24 runs every process.
The `@teacss/core` 0.8.5 peer range on `@teacss/engine` is `>=0.9.0`; Bun
installs the pair and the engine accepts core 0.8.5 through its
own `engineCompat.core` ([ADR-0003](../adrs/ADR-0003-published-packages.md)).
A `--local` mode that links sibling checkouts exists for development; a report
never uses it.

Each subject process reports the `.node` files in
`process.report.getReport().sharedObjects` at exit. A sample whose loaded set
differs from the table above is invalid.

## Tiers

### `engine`: candidates to CSS

Input: the corpus candidates as strings, already extracted. No file scanning.
Output: the CSS string. Preflight and base styles are off on every subject so
the output holds the theme variables and the utilities only.

| Subject | Timed call |
| --- | --- |
| `teacss-ts`, `teacss-rs` | `createGenerator({ presets: [presetStandard()], engine })` then `generate(tokens, { preflights: false, minify: true })` |
| `tailwind-v4` | `compile(css, { base })` with `@layer theme, utilities; @import "tailwindcss/theme.css" layer(theme); @import "tailwindcss/utilities.css" layer(utilities);` then `build(candidates)` |
| `vite-baseline` | not measured in this tier |

Two scenarios:

- `engine/cold`: a fresh process; the timed region starts before the subject
  module is imported and ends when the CSS string is returned. It includes
  module loading and native binding loading.
- `engine/warm`: a fresh process runs three untimed iterations, then ten timed
  iterations. An iteration constructs a new generator or compiler and produces
  the full corpus. Each timed iteration is one sample; three processes give
  the thirty samples of a cell.

### `build`: `vite build` to production CSS

Input: a generated project on disk (`index.html`, one entry module importing
the corpus modules, the subject's CSS entry and Vite config). Output: the CSS
asset in `dist/`. One sample is one `vite build` in a fresh process, timed
from spawn to exit by the orchestrator. The `vite-baseline` subject builds
the same project with no CSS engine; the report shows each subject's time and
its delta over the baseline in the same cell.

Subject configuration in this tier:

- `teacss-*`: `index.css` at the project root with `@presets "standard"; @source "./src/**/*.js"; @teacss;`, each corpus module carries `// @teacss-include`, the entry imports `virtual:teacss.css`, `pluginTeacss({ engine })`.
- `tailwind-v4`: `src/style.css` with `@import "tailwindcss" source(none); @source "./**/*.js";`, `@tailwindcss/vite`.
- `minify` stays at each plugin's production default; the report records the
  output bytes raw and gzip.

## Corpus

Generated by `packages/benchmark/features/corpus` from `(seed, utilities,
files, pairTableVersion)` with a seeded PRNG; `Corpus.hash` is the SHA-256 of
the generated case list and every sample carries it. A paired case is:

```ts
interface PairedCase {
  readonly teacss: string;    // "p:4@hover"
  readonly tailwind: string;  // "hover:p-4"
  readonly properties: readonly string[]; // ["padding"]
  readonly conditions: readonly string[]; // ["hover"]
}
```

The pair table lists only families both tools support natively: spacing
(`p`, `m` and their edges), colors with opacity, font size, radius, grid
columns, arbitrary lengths and colors, and the conditions `hover`, `focus`,
`active`, `first`, `dark`, `sm`, `md`, `lg`. The table and the family
distribution of each generated corpus are published with the report
([ADR-0002](../adrs/ADR-0002-paired-corpus.md)).

Cases are spread over `files` modules, each assigning markup strings with the
classes to `innerHTML`, so both scanners see complete class tokens.

## Scale matrix

| Dimension | Values |
| --- | --- |
| utilities | 1 000, 5 000, 20 000 |
| files | 3, 30, 300 |
| samples per subject per cell | 30 |

Both tiers run the full matrix. A published report that ran a subset says so
in its header and shows no number for a cell it did not run.

## Run protocol

1. The orchestrator refuses to start when the one-minute load average exceeds
   20 % of the logical core count; `--allow-busy` overrides it and the report
   header says so.
2. Every sample runs in a fresh child process that loads exactly one subject.
   The orchestrator never imports a subject.
3. Subjects are interleaved: each round runs every subject once in a random
   order, and rounds repeat until every cell has its samples.
4. A sample records wall time, CPU user and system time, maximum RSS, output
   bytes raw and gzip, the SHA-256 of the output and the loaded `.node` list.
5. A subject process that exits non-zero, times out, reports a TeaCSS
   fallback line, or reports an unexpected native-module set invalidates the
   whole run: the orchestrator stops and writes nothing to `results/`.
6. Within one run, every sample of a subject and cell must produce the same
   output hash; a mismatch invalidates the run.
7. A profiling pass (`node --cpu-prof`) runs once per subject and tier after
   the measured run and is never counted; the report lists its top three
   self-time frames as the limiter.

## Equivalence

Checked before the measured run on the same corpus; a failure stops the run.

- Strong: the `teacss-ts` and `teacss-rs` outputs are byte-identical in both
  tiers.
- Coverage: for every case, the subject's selector (escaped) occurs in its
  output; a missing selector is listed and fails the check.
- Structural: both outputs are parsed; for every case the set of property
  names and the condition structure (pseudo-class, media query) match the
  case's `properties` and `conditions`. Values are not compared, because the
  two design systems differ in palettes and units. The report states this
  limit in its own words.

## Statistics

Per subject and cell, over the 30 samples: median, interquartile range, 95th
percentile, minimum. In the `build` tier, the delta over the baseline median.

Two subjects differ when a two-sided Mann-Whitney U test gives p < 0.01 and
the medians differ by more than the larger of the two interquartile ranges.
Otherwise the report says "no measurable difference". A ratio is printed only
for a pair that differs.

## Environment record

Each results file carries: CPU model, logical cores, memory, OS and version,
Node version, Bun version, the SHA-256 of `bun.lock`, the git commit of
this repository, every subject's package versions from its own `describe()`,
the corpus hash and generator parameters, the spec revision, the one-minute
load average before and after each cell, and the start and end time.

## Report

`bench report <results.json>` is deterministic: the same input produces the
same Markdown and JSON summary. The Markdown holds, in this order: the
verdict in one paragraph per tier, one table per tier and scale cell, the
environment block, the versions block, the corpus block, the limiter section,
the answers to the seven benchmark-checklist questions, and the known limits
(structural rather than value equivalence, the author's relation to TeaCSS,
CI runner noise).

## Acceptance and verification

| Requirement | Check |
| --- | --- |
| Subjects load what the table says | `bench verify` compares each subject's reported `.node` list with the table |
| Rust never silently falls back | `TEACSS_ENGINE_STRICT=1` is set and a fallback line fails the run (test with a planted unsupported option) |
| Same work | strong, coverage and structural equivalence pass on the run's corpus |
| Determinism | the same `(seed, utilities, files)` yields the same corpus hash twice; the same results file yields the same report twice |
| Protocol | the orchestrator refuses on load, invalidates on error, interleaves (unit tests on the measure feature with fake subjects) |
| Reproduction | a fresh clone, `bun install --frozen-lockfile`, `bun run bench` completes the matrix and `bench report` regenerates the committed report byte for byte |

## Open questions

None that block implementation. The owner's three defaults (English report,
20 000 utilities as the upper bound, the dev tier in the second phase) are
recorded in the proposal's status and can be changed before the first
published run.
