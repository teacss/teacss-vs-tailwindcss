# Spec v01.1: Benchmark protocol

This document is the pre-registered method. It is accepted and committed
before the first published run. A published report follows the revision it
names; a deviation is recorded in the report, never by editing this file to
fit a result. A change bumps `spec-revision`.

Revision 2 (2026-10-21) moved the TeaCSS subjects from 0.8.5 to 0.9.0-alpha.1
before the first published run. Revision 3 (2026-10-22) moves them to
0.9.0-alpha.2, the release that carries the build-pipeline fixes the first run
motivated, and adds the Node version gate; the engine stays 0.8.5-alpha.4.

Revision 4 (2026-10-24) ends a build sample when the tool's build returns. The
subject process had hashed, compressed and counted the rules of its output,
removed its workspace and read its native modules before exiting, and all of
that fell inside the spawn-to-exit time. Those steps cost about 50 ms for a
1 MB stylesheet and about 150 ms for a 2.8 MB one at 20 000 utilities, so the
tool with the larger output was timed slower than its build. The subject now
reports how long that work took and its CPU and memory when the build
returned; the sample's wall time is the spawn-to-exit time minus that work,
and its CPU and RSS are the values at the build's return. Build samples of
revisions 3 and 4 are not comparable.

Revision 10 (2026-11-03) moves the teacss-rs subjects to 0.10.5, where
`@teacss/vite` passes the generated sheet through Vite's CSS pipeline
(teacss-rs #724). The two Vite plugins compare byte for byte again, as
revision 9 said they would once a fixed release was measured. On 1 000
utilities in 30 files, `@teacss/vite-ts` 0.10.3 and `@teacss/vite` 0.10.5
wrote the same 103 677 bytes, and so do `@teacss/vite-ts` 0.10.4 and 0.10.5 with
`@teacss/vite` 0.10.5. Engines and bundler plugins compare byte for
byte; the two CLIs compare byte for byte once each bundled font's URL is
reduced to its digest. The dev servers are not verified, and their sheets
differ in the same way: `@teacss/vite` inlines the bundled fonts as data URIs
in development and `@teacss/vite-ts` links them, so the report counts the Vite
build and the dev server apart. Both ecosystems at 0.10.6 (2026-11-04) write
the same 103 677 bytes again. `@teacss/vite` 0.10.6 links the bundled fonts
in development as `@teacss/vite-ts` does, and the two dev sheets then differ
only in the font rules, where `@teacss/vite-ts` writes `url()` as `URL(`.
With that case made the same, the two sheets are byte-identical.
`@teacss/vite` 0.10.7 writes `URL(` too, so Vite skips PostCSS on its dev
sheet as well, and the two dev sheets are byte-identical in every dev sample
at 1 000 x 30 and 20 000 x 300. Both ecosystems at 0.10.8 write the same
bytes as before, dev sheets included.

Revision 9 (2026-11-03) moves the TeaCSS subjects to 0.10. TeaCSS is now two
ecosystems that share no package: teacss-ts 0.10.3 (`@teacss/core`,
`@teacss/preset-standard`, `@teacss/vite-ts`, `@teacss/cli`) and teacss-rs
0.10.4 (`@teacss/engine`, `@teacss/vite`, `@teacss/postcss`, `@teacss/rsbuild`,
`@teacss/bun`, `teacss`). Neither has an engine switch or a fallback, so
`TEACSS_ENGINE_STRICT` is gone, and a subject's native-module expectation is
what proves its engine. The teacss-rs packages need Node 26, so every process
runs on Node 26.12.0, and Bun moves to 1.4.4. Equivalence changes in three
places:

- Engines still compare byte for byte.
- The two Vite plugins can no longer write the same bytes. `@teacss/vite-ts`
  passes the generated sheet through Lightning CSS, which prints it compactly
  and adds prefixes such as `-webkit-text-decoration`. `@teacss/vite` splices
  the sheet into the bundle after Vite's minifier, so it ships the engine's
  text. On 1 000 utilities in 30 files the two builds are 103 677 and
  105 233 bytes. This is a teacss-rs defect: the generated sheet skips Vite's
  CSS pipeline. Until a fixed `@teacss/vite` is measured, a pair of plugins
  must select the same classes with the same properties; after that, the
  pair compares byte for byte again. The two command lines, which no bundler touches,
  still compare byte for byte once each bundled font's URL is reduced to its
  digest: `teacss` inlines the fonts and `teacss-cli` writes them to files.
- Every build subject is built a second time with another stylesheet
  imported ahead of its own, and must keep every case. `@teacss/vite` 0.10.3
  under Vite 8 passed the first build and lost every utility in the second,
  leaving a 37-byte sheet.

`bench cases` adds a table of the behaviours the 0.10 upgrade guide names
(§Behaviour cases). Samples of revisions 8 and 9 are not comparable: the
packages, Node and Bun all changed.

Revision 8 (2026-10-25) also checks the load during a run. The start gate
only looks at the one-minute load before the first sample. A run on
2026-10-25 passed it at 19 % and then recorded 37 % to 108 % around its
cells while another application kept the machine busy; even the warm engine
medians moved by 7 % to 15 %. It was discarded. A run now writes no record
when the load share at either end of any cell exceeds 50 %, unless it was
started with `--allow-busy`. Every published run so far stayed at or below
42 %. Samples of revisions 7 and 8 are comparable.

Revision 7 (2026-10-25) loads in each subject process only the packages its
task uses. The Vite subject modules imported every tool package at the top,
so a build also loaded the engine-tier packages and the other pipeline's
plugin: TeaCSS's builds loaded `@teacss/postcss`, and Tailwind's loaded
`@tailwindcss/postcss` with PostCSS. An engine-tier cold sample, which
times the subject's import, also loaded Vite and both plugins. A user's
`vite build` loads none of that. Each subject now imports a package inside
the task that needs it. An A/B on the same machine moved builds by less than
the noise (TeaCSS by 4 to 9 ms, Tailwind by -1 to +5 ms at 1 000 utilities)
and cold engine samples by 38 to 64 ms. The Tailwind engine tier no longer
loads Oxide, which only its scanner uses, so Oxide is required only of build
and dev processes. Engine-cold and build samples of revisions 6 and 7 are not
comparable.

Revision 6 (2026-10-25) sets `NODE_ENV` the way the CLIs do. The `vite` and
`rsbuild` CLIs set it before they load a config, to `production` for a build
and to `development` for a dev server. The harness creates each plugin before
it calls the tool's API, and the tool sets `NODE_ENV` only inside that call,
so a plugin that read `NODE_ENV` when it was created saw it unset. For
`@teacss/vite` up to 0.9.2 that meant the dev server ran in TeaCSS's build
mode, which skips the dev-mode rule details and was about 70 ms faster per
round at 20 000 utilities with the TypeScript engine than what `vite dev`
users get. `@tailwindcss/postcss` skips its production optimization when
`NODE_ENV` is not `production`. The orchestrator now sets `NODE_ENV` for
every build and dev task of a Node subject; engine tasks and Bun subjects run
without it. Build and dev samples of revisions 5 and 6 are not comparable.

Revision 5 (2026-10-24) gives every Node build subject Node's compile cache.
The `vite` CLI (8.3.4) and the `rsbuild` CLI (2.2.14) call
`module.enableCompileCache()` before they load anything, so a user who runs
`vite build` or `rsbuild build` gets the cache whatever CSS tool the project
uses. The harness calls each tool's `build()` API, which does not enable it.
A tool that switched the cache on from inside its own plugin would then be the
only subject with it, and because the cache covers the whole process, it would
also speed up the bundler. The orchestrator now sets `NODE_COMPILE_CACHE` for
every build and dev task of a Node subject. It does not set it for engine
tasks, nor for Bun subjects: Bun honours the variable but has no Node CLI that
enables it. Each run empties the cache directory before its equivalence checks,
which build every subject once and so fill the cache before anything is timed.
Build samples of revisions 4 and 5 are not comparable.

## Outcome and scope

A reader outside TeaCSS can clone this repository, run one command and get
the same comparison, on their machine, of four subjects across two tiers and
a scale matrix, with every number traceable to raw samples and every subject
proven to have done the same work.

Excluded: the development-server incremental tier (second phase), Tailwind
v3, UnoCSS, teacss-zig, and a report website.

## Subjects

| Id | Packages (exact) | Engine switch | Native modules that must be loaded |
| --- | --- | --- | --- |
| `vite-baseline` | `vite` 8.3.4 | none | none |
| `teacss-ts` | `vite` 8.3.4, `@teacss/vite-ts` 0.10.8, `@teacss/core` 0.10.8, `@teacss/preset-standard` 0.10.8 | none: teacss-ts runs only its TypeScript engine since 0.10 | none; `teacss-engine` must not load |
| `teacss-rs` | `vite` 8.3.4, `@teacss/vite` 0.10.8, `@teacss/engine` 0.10.8 and its platform package | none: teacss-rs has no fallback since 0.10 | `teacss-engine.<platform>.node` |
| `tailwind-v4` | `vite` 8.3.4, `tailwindcss` 4.3.3, `@tailwindcss/vite` 4.3.3, `@tailwindcss/node` 4.3.3, `@tailwindcss/oxide` 4.3.3 | none | `tailwindcss-oxide.<platform>.node`; `lightningcss.<platform>.node` is loaded by both Tailwind and TeaCSS |

Every subject runs with its documented production configuration and the
packages as published on npm, installed with Bun from the committed `bun.lock`
([ADR-0004](../adrs/ADR-0004-bun-package-manager.md)); Node 26 runs every
process, because the teacss-rs packages require it
([ADR-0005](../adrs/ADR-0005-two-teacss-ecosystems.md)).
For development, `bun run bench:link link --ts <teacss-ts checkout>` points the
teacss subjects' `@teacss/core`, `@teacss/vite-ts` and `@teacss/preset-standard`
at a built checkout, or `bench:link link --rs <teacss-rs checkout>` points every
`@teacss/engine` the published packages resolve at that checkout's built
`packages/engine`. The two ecosystems share no package, so one link never
changes the other.
`bench:link unlink` restores the lockfile packages. Each subject reports every
package resolved outside `node_modules/.bun`, and a report from such a run opens
with "Local build, not for publication"; a published report never has one.

Each subject process reports the `.node` files in
`process.report.getReport().sharedObjects` at exit. A sample whose loaded set
differs from the table above is invalid.

## Tiers

### `engine`: candidates to CSS

Input: the corpus candidates as strings, already extracted. No file scanning.
Output: the CSS string. Preflight and base styles are off on every subject so
the output holds the theme variables and the utilities only.

| Subject | Timed call |
| --- | --- |
| `teacss-ts` | `createGenerator({ presets: [presetStandard()] })` then `generate(tokens, { preflights: false, minify: true })` |
| `teacss-rs` | `createProject({ root, entry })` on an entry holding `@presets "standard"; @teacss;`, then `engine.generate({ kind: "tokens", tokens }, { preflights: false, minify: true })`; neither engine is released inside the timed call |
| `tailwind-v4` | `compile(css, { base })` with `@layer theme, utilities; @import "tailwindcss/theme.css" layer(theme); @import "tailwindcss/utilities.css" layer(utilities);` then `build(candidates)` |
| `vite-baseline` | not measured in this tier |

Two scenarios:

- `engine/cold`: a fresh process; the timed region starts before the subject
  module is imported and ends when the CSS string is returned. It includes
  module loading and native binding loading.
- `engine/warm`: a fresh process runs three untimed iterations, then ten timed
  iterations. An iteration constructs a new generator or compiler and produces
  the full corpus. Each timed iteration is one sample; three processes give
  the thirty samples of a cell.

### `build`: `vite build` to production CSS

Input: a generated project on disk (`index.html`, one entry module importing
the corpus modules, the subject's CSS entry and Vite config). Output: the CSS
asset in `dist/`. One sample is one `vite build` in a fresh process, timed
from spawn to exit by the orchestrator, minus the harness's own work after the
build returns (revision 4), with Node's compile cache on and `NODE_ENV=production`, as the `vite` CLI
sets them (revisions 5 and 6). The `vite-baseline` subject builds
the same project with no CSS engine; the report shows each subject's time and
its delta over the baseline in the same cell.

Subject configuration in this tier:

- `teacss-*`: `index.css` at the project root with `@presets "standard"; @source "./src/**/*.js"; @teacss;`, each corpus module carries `// @teacss-include`, the entry imports `virtual:teacss.css`; `pluginTeacss()` from `@teacss/vite-ts` for teacss-ts and `teacss()` from `@teacss/vite` for teacss-rs.
- `tailwind-v4`: `src/style.css` with `@import "tailwindcss" source(none); @source "./**/*.js";`, `@tailwindcss/vite`.
- `minify` stays at each plugin's production default; the report records the
  output bytes raw and gzip.

## Corpus

Generated by `packages/benchmark/features/corpus` from `(seed, utilities,
files, pairTableVersion)` with a seeded PRNG; `Corpus.hash` is the SHA-256 of
the generated case list and every sample carries it. A paired case is:

```ts
interface PairedCase {
  readonly teacss: string;    // "p:4@hover"
  readonly tailwind: string;  // "hover:p-4"
  readonly properties: readonly string[]; // ["padding"]
  readonly conditions: readonly string[]; // ["hover"]
}
```

The pair table lists only families both tools support natively: spacing
(`p`, `m` and their edges), colors with opacity, font size, radius, grid
columns, arbitrary lengths and colors, and the conditions `hover`, `focus`,
`active`, `first`, `dark`, `sm`, `md`, `lg`. The table and the family
distribution of each generated corpus are published with the report
([ADR-0002](../adrs/ADR-0002-paired-corpus.md)).

Cases are spread over `files` modules, each assigning markup strings with the
classes to `innerHTML`, so both scanners see complete class tokens.

## Behaviour cases

`bench cases` runs a fixed table of behaviours the 0.10 upgrade guide names,
on the published packages, through the same subject processes. Each case names
its release, the subjects it applies to, and the classes the sheet must select,
must not select, or the text it must hold; each lists a form that must work,
so an absence alone never passes a case. Engine cases send tokens; build cases
send a small project, whose own `index.css` replaces the subject's entry when
the case gives one. A case is a regression check, not a measurement, and no
number comes from it.

| Dimension | Values |
| --- | --- |
| utilities | 1 000, 5 000, 20 000 |
| files | 3, 30, 300 |

Both tiers run the full matrix. A published report that ran a subset says so
in its header and shows no number for a cell it did not run.

## Run protocol

1. The orchestrator refuses to start when the one-minute load average exceeds
   20 % of the logical core count; `--allow-busy` overrides it and the report
   header says so.
   It also refuses when the running Node version differs from `.node-version`,
   because every subject process inherits the orchestrator's binary;
   `--allow-node-mismatch` overrides it and the environment block shows the
   version that ran.
2. Every sample runs in a fresh child process that loads exactly one subject.
   The orchestrator never imports a subject.
3. Subjects are interleaved: each round runs every subject once in a random
   order, and rounds repeat until every cell has its samples.
4. A sample records wall time, CPU user and system time, maximum RSS, output
   bytes raw and gzip, the SHA-256 of the output and the loaded `.node` list.
5. A subject process that exits non-zero, times out, reports a TeaCSS
   fallback line, or reports an unexpected native-module set invalidates the
   whole run: the orchestrator stops and writes nothing to `results/`.
6. Within one run, every sample of a subject and cell must produce the same
   output hash; a mismatch invalidates the run.
7. A profiling pass (`node --cpu-prof`) runs once per subject and tier after
   the measured run and is never counted; the report lists its top three
   self-time frames as the limiter.

## Equivalence

Checked before the measured run on the same corpus; a failure stops the run.

- Strong: the `teacss-ts` and `teacss-rs` engine outputs are byte-identical.
  In the build tier, a pair of bundler plugins selects the same classes with
  the same declared properties, and the two command lines write byte-identical
  sheets once each bundled font's URL is reduced to its digest (revision 9).
- Leading stylesheet: every build subject except the command lines is built a
  second time with the first corpus module importing another stylesheet, so
  every entry loads it ahead of the tool's own. That stylesheet must survive,
  stay ahead of every case, and every case must still pass the structural
  check (revision 9).
- Coverage: for every case, the subject's selector (escaped) occurs in its
  output; a missing selector is listed and fails the check.
- Structural: both outputs are parsed; for every case the set of property
  names and the condition structure (pseudo-class, media query) match the
  case's `properties` and `conditions`. Values are not compared, because the
  two design systems differ in palettes and units. The report states this
  limit in its own words.

## Statistics

Per subject and cell, over the 30 samples: median, interquartile range, 95th
percentile, minimum. In the `build` tier, the delta over the baseline median.

Two subjects differ when a two-sided Mann-Whitney U test gives p < 0.01 and
the medians differ by more than the larger of the two interquartile ranges.
Otherwise the report says "no measurable difference". A ratio is printed only
for a pair that differs.

## Environment record

Each results file carries: CPU model, logical cores, memory, OS and version,
Node version, Bun version, the SHA-256 of `bun.lock`, the git commit of
this repository, every subject's package versions from its own `describe()`,
the corpus hash and generator parameters, the spec revision, the one-minute
load average before and after each cell, and the start and end time.

## Report

`bench report <results.json>` is deterministic: the same input produces the
same Markdown and JSON summary. The Markdown holds, in this order: the
verdict in one paragraph per tier, one table per tier and scale cell, the
environment block, the versions block, the corpus block, the limiter section,
the answers to the seven benchmark-checklist questions, and the known limits
(structural rather than value equivalence, the author's relation to TeaCSS,
CI runner noise).

## Acceptance and verification

| Requirement | Check |
| --- | --- |
| Subjects load what the table says | `bench verify` compares each subject's reported `.node` list with the table |
| Each ecosystem runs its own engine | `teacss-rs` subjects must load `teacss-engine` and `teacss-ts` subjects must not; both are checked on every response (revision 9; before it, `TEACSS_ENGINE_STRICT=1`) |
| A stylesheet ahead of the tool's own loses nothing | the leading-stylesheet build of every corpus passes; a planted `@teacss/vite` 0.10.3 fails it |
| The 0.10 behaviours hold | `bench cases` passes on the published packages; `@teacss/vite` 0.10.2 fails its two unquoted `url()` cases |
| Same work | strong, coverage and structural equivalence pass on the run's corpus |
| Determinism | the same `(seed, utilities, files)` yields the same corpus hash twice; the same results file yields the same report twice |
| Protocol | the orchestrator refuses on load, invalidates on error, interleaves (unit tests on the measure feature with fake subjects) |
| Reproduction | a fresh clone, `bun install --frozen-lockfile`, `bun run bench` completes the matrix and `bench report` regenerates the committed report byte for byte |

## Open questions

None that block implementation. The owner's three defaults (English report,
20 000 utilities as the upper bound, the dev tier in the second phase) are
recorded in the proposal's status and can be changed before the first
published run.
