# TeaCSS 0.9.3：Rust 引擎成了默认，以及一次更正

**结论。** TeaCSS 0.9.2 和 0.9.3 生成的 CSS 与 0.9.0 逐字节相同。用户会感觉到的变化是默认引擎换成了 Rust：不写 `engine` 选项的项目，从 0.9.2 起就用 Rust 引擎。在 20 000 个类、300 个文件的项目里：

- 开发服务器里保存一个文件，Rust 引擎要 77 ms，Tailwind CSS v4 要 324 ms；
- Vite 生产构建里，CSS 部分 Rust 引擎加 220 ms，Tailwind 加 574 ms。

这一轮前后改了四处测法，并更正了之前的一个错误结论。

## 更正：TypeScript 引擎的开发服务器并没有在 0.9.3 变慢

上一版报告和本文的上一版说，0.9.3 让 TypeScript 引擎的开发服务器慢了约三分之一。这个结论是错的，原因在基准程序：

- 基准程序先创建插件，再调用 Vite 的 API，而 Vite 是在这个调用里面才设置 `NODE_ENV` 的。
- 0.9.2 及以前的 `@teacss/vite` 在插件创建时就读取 `NODE_ENV`，读到的是空值，于是开发服务器跑的是 TeaCSS 的「构建模式」。构建模式省掉了开发模式里的规则细节，所以更快。
- 用户在命令行里跑 `vite dev` 时，Vite 会在加载配置之前设好 `NODE_ENV`，所以用户拿到的一直是开发模式。
- 0.9.3 把读取推迟到了第一次钩子调用，这才和用户一致。

在 0.9.1 上只设 `NODE_ENV=development`，TypeScript 引擎的开发服务器就从 245 ms 变成 313 ms；Rust 引擎几乎不变（74 → 75 ms）。所以之前各份报告里，TypeScript 引擎的开发服务器数字都偏快，对 TeaCSS 有利。0.9.3 的数字才代表用户的真实体验。每份旧报告的审核里都补记了这一点。

这个问题是 teacss-ts 查出来的，我复现确认后改了测法。

## 四处测法的修订

前两处是为了让基准和用户在命令行里拿到的环境一致：

1. **编译缓存（协议修订 5）。** `vite`、`rsbuild` 和 `astro` 的命令行都会打开 Node 的编译缓存。基准以前谁都没开；现在所有 Node 构建和开发服务器都开。这一项是因为 teacss-ts 的 B5 让 TeaCSS 插件自己打开编译缓存：如果只有 TeaCSS 开，它就会占一个用户拿不到的便宜。
2. **`NODE_ENV`（协议修订 6）。** 构建时设为 `production`，开发服务器设为 `development`，和命令行一样。这修正了上面那个偏差，也让 Tailwind 的 PostCSS 插件在构建时做它本该做的生产优化。它的产出现在和 Tailwind 的 Vite 插件逐字节相同，构建也因此慢了约 140 ms：用户本来就要付这笔时间，以前的测法漏掉了。

Bun 没有这样的命令行，所以 Bun 组两样都不设。

后两处是剖析小项目时发现的：

3. **只加载本任务用到的包（协议修订 7）。** 测试对象文件以前在开头导入了所有包：TeaCSS 的 Vite 构建会多加载 `@teacss/postcss`，Tailwind 的会多加载 `@tailwindcss/postcss` 和 PostCSS。引擎层「全新进程」那一项的计时里，还包括了加载 Vite 和两种插件。改了之后，构建的变化在噪声以内，冷启动对所有工具都少了 40 到 60 ms。
4. **中途负载过高就作废（协议修订 8）。** 以前只在开跑前检查负载。有一轮开跑后，别的程序让负载一直在 40% 上下、最高到 108%，那一轮作废重跑了。现在任何一格前后的负载份额超过 50%，整轮都不写记录。

修订后，构建、开发服务器和引擎冷启动的数字不能直接和以前的报告比，引擎层其他数字可以比。

## 20 000 个类、300 个文件

每格 30 次交替运行的中位数：

| 场景 | TeaCSS（Rust 引擎） | Tailwind CSS v4 | TeaCSS（TypeScript 引擎） |
| --- | --- | --- | --- |
| 全新进程，从启动到生成完 | 103 ms | 332 ms | 692 ms |
| 在已经启动的进程里生成全部 CSS | 52 ms | 232 ms | 495 ms |
| 往运行中的引擎里加 10 个类 | 18 ms | 141 ms | 112 ms |
| 开发服务器里保存一个带 10 个新类的文件 | 77 ms | 324 ms | 311 ms |
| Vite 生产构建 | 405 ms | 760 ms | 1 016 ms |

这一轮在晚上跑，机器比下午慢了 5% 到 8%，三个工具一样。所以毫秒数和以前的报告不能直接比，倍数可以比。

各构建工具里，CSS 工具在基线之上加的时间：

| 构建工具 | 基线 | TeaCSS（Rust 引擎） | Tailwind CSS v4 |
| --- | --- | --- | --- |
| Vite | 185 ms | +220 ms | +574 ms |
| Vite + PostCSS | 185 ms | +269 ms | +747 ms |
| Rsbuild | 180 ms | +304 ms | +992 ms |
| Bun（Bun 运行时） | 73 ms | +153 ms | +340 ms |

117 组正面比较：Rust 引擎赢 110 组，Tailwind 赢 3 组，4 组无可测差异。

## 对 TeaCSS 仍然不利的地方

- **小项目构建。** 1 000 个类时，15 张构建表里：
  - Tailwind 在 3 张里可测地更快：Bun 的 3 个和 30 个文件，各领先 15 ms；Vite 的 300 个文件，领先 13 ms。
  - Rust 引擎在 8 张里可测地更快：Vite、默认配置、PostCSS、Rsbuild 在 3 个和 30 个文件时，领先 9 到 15 ms。
  - 4 张无可测差异，都是 300 个文件。
  - 剩下的差距来自固定的启动成本和每个文件的提取，已经写成七张优化卡片交给 teacss-ts 和 teacss-rs，见[小项目优化卡片](../knowledge/optimization-cards-2026-10-25-small-projects.md)。
- **TypeScript 引擎的构建仍比 Tailwind 慢。** 45 组构建比较里 42 组更慢。
- **TypeScript 引擎占内存更多。** 生成一次后常驻约 650 到 800 MB，Rust 引擎约 380 MB。报告里 0.9.1 的 652 MB 和 0.9.3 的 792 MB 并不是版本差异：同一个版本连跑两次，一次约 653 MB，一次约 770 MB，取决于垃圾回收最后一次运行的时机。

## 公平性

方法与前几轮相同：

- 发布版、Node 24.14.1；
- 计时前逐类校验，78 000 个用例零差异；
- 所有对象逐轮随机交替，每格 30 次；
- 负载连续两分钟低于 2.4 才开始，各格负载份额 17% 到 37%，任何一格超过 50% 就作废；
- 构建计时到构建返回为止；
- 所有 Node 构建和开发服务器都使用命令行会设的编译缓存与 `NODE_ENV`，并且只加载本任务用到的包。

每个 TeaCSS 对象都显式指定引擎，所以「TypeScript 引擎」那一列确实是 TypeScript 引擎。3 510 对样本里，两种引擎的产出逐字节相同。

限制不变：

- 只有一台 Apple M2 Max，Linux 交叉验证未跑；
- 只有生成的配对语料，社区语料还在等仓库清单；
- 本基准的作者也开发 TeaCSS。
