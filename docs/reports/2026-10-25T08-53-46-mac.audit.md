## What revision 6 changed

Against the fifth report, same packages and machine, the only protocol change is `NODE_ENV`:

- **Tailwind's PostCSS builds** got slower: 799.7 → 939.1 ms at 20 000 x 300. `@tailwindcss/postcss` runs its production optimization only when `NODE_ENV` is `production`. It now does what `vite build` users get, and its output matches the Tailwind Vite plugin byte for byte. Under revision 5 and earlier, that subject skipped work its users do.
- **Every other subject** moved by less than 2 % at 20 000 x 300. That includes the TypeScript engine's dev rounds (301.0 → 299.2 ms): 0.9.3 already read `NODE_ENV` after Vite set it.
- **The earlier reports' TypeScript-engine dev rounds** were too fast, because `@teacss/vite` up to 0.9.2 read `NODE_ENV` before Vite set it and ran in TeaCSS's build mode. On 0.9.1, setting `NODE_ENV=development` took dev +10 at 20 000 x 300 from 244.7 to 312.6 ms. Each earlier audit carries a correction.

## The seven questions

1. **Why not double?**
   - The warm teacss-rs engine (50 ms) is 23 % of the 220 ms the CSS adds to a Vite build. The rest is the plugin pipeline.
   - Tailwind's Vite build spends about a fifth of its profile in lightningcss.
2. **Was it tuned?**
   - Every subject ran its published package with the entry its documentation gives, with what the CLIs set before loading a config.
   - The `-default` subjects took about 1.00x the tuned build time.
   - Every TeaCSS subject ran with `TEACSS_ENGINE_STRICT=1`.
3. **Did it break limits?** No. The largest output is Tailwind's under Bun, 3.2 MB. Medians grow with the utility count in every tier.
4. **Did it error?** No. A run with any error, timeout, fallback, or missing or duplicate native binary writes no record, and this record exists.
5. **Does it reproduce?**
   - Each of the 396 groups has 30 interleaved samples. The median IQR is 2.8 % of the median.
   - The noisiest groups are Tailwind's warm and +10 engine (20 % to 33 %), and the +100 scenarios at 1 000 utilities, which take a few milliseconds (20 % to 24 %).
   - None carries a headline.
6. **Does it matter?**
   - A dev save takes 70 ms with the Rust engine, 299 ms with the TypeScript engine and 323 ms with Tailwind.
   - At the largest cell, the CSS work adds 220 ms for teacss-rs, 558 ms for Tailwind and 819 ms for teacss-ts to a 179 ms Vite build.
   - In a 1 000-class project the two are within 15 ms either way.
7. **Did it even happen?** Yes.
   - Every warm and build group produced one hash. The build hashes are the same as in 0.9.0: `ee274f23…ef007` at 1 000 x 300 and `f4ea28ce…a96d4` at 20 000 x 300.
   - teacss-ts and teacss-rs produced byte-identical output in all 3 510 sample pairs across the five groups.

## Limits of this run

- **One machine:** an Apple M2 Max with 12 cores, running macOS. The Linux cross-check has not run.
- **One corpus.** The community corpus still waits for the owner's repository list.
- **The Bun group** runs in the Bun runtime, with neither the compile cache nor `NODE_ENV`. Its baseline and absolute times compare runtimes as well as CSS tools; the deltas over its own baseline are the comparison.
- **The author of this benchmark also develops TeaCSS.** The method, the pair table and the raw samples are published, and the run is reproducible from a clean clone.

## Correction: packages loaded outside the task (2026-10-25)

The Vite subject modules imported every tool package at the top. Each build here also loaded packages a user's `vite build` would not: `@teacss/postcss` for TeaCSS, and `@tailwindcss/postcss` with PostCSS for Tailwind. Each cold engine sample, which times the subject's import, also loaded Vite and both plugins. Spec v01.1 revision 7 loads only what the task uses. On the same machine, the cold engine samples dropped by 38 to 64 ms for every tool, and builds moved by less than the noise, TeaCSS's by 4 to 9 ms and Tailwind's by -1 to +5 ms at 1 000 utilities. Read this report's engine-cold numbers as including about 40 to 60 ms of loading that no user pays.
