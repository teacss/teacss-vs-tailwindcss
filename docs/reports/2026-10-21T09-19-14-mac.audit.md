# Audit of run 2026-10-21T09:19:14Z

This audit reviews [the report](2026-10-21T09-19-14-mac.md) against the benchmark checklist. The report is generated from [the raw record](../../results/2026-10-21T09-19-14-mac.json) by `bun run bench:report`, and it regenerates byte for byte. This audit is written by hand, so it is kept in a separate file.

## Verdict

The numbers stand. Every subject did the same work, all 2 700 samples succeeded, and every reported difference is a complete separation: Cliff's delta is -1.00 in every one of the 52 differing comparisons. One comparison is close: in the warm engine at 1 000 utilities, teacss-rs and Tailwind v4 show no measurable difference.

At 20 000 utilities in 300 files:

| Tier | Lowest median | teacss-rs | Tailwind v4 | teacss-ts |
| --- | --- | --- | --- | --- |
| Engine, cold process | 257 ms (teacss-rs) | 1.00x | 1.48x | 2.59x |
| Engine, warm process | 155 ms (teacss-rs) | 1.00x | 1.43x | 2.87x |
| Vite build | 819 ms (Tailwind v4) | 2.13x | 1.00x | 4.58x |

The Rust engine is faster than Tailwind's compiler, but a TeaCSS Vite build is still slower than a Tailwind one. The engine is not what the build waits on.

## The seven questions

1. **Why not double?** In the warm engine, teacss-rs spends 74 % of its profile in the facade's `generate` (`@teacss/engine/src/facade/generator.mjs:416`). The profiler attributes the native call to that JavaScript frame, so the split between facade and Rust is not visible. Tailwind's warm engine spends 13 % in the garbage collector, which also explains its wider spread. In the build tier, the teacss-rs delta over the baseline is 1 490 ms, and the warm engine accounts for about 155 ms of it. The top build frames are lightningcss (17 %), the garbage collector (10 %) and `generate` (7 %). The other two thirds are spread across the `@teacss/vite` plugin pipeline and have no single dominant frame. **That build limiter is inconclusive** beyond the statement that it is not the engine. A follow-up profile ([build profile](../knowledge/teacss-vite-build-profile-2026-10-21.md)) accounts for 99 % of the delta. 84 % is `buildEnd`, which re-parses the finished stylesheet three times: lightningcss once and css-tree twice.
2. **Was it tuned?** Every subject ran its published package with its documented production configuration: `@teacss/vite` 0.9.0-alpha.1 with the engine it depends on, `@tailwindcss/vite` 4.3.3, and Vite 8.3.4 defaults with minification on. No subject has a setting another lacks.
3. **Did it break limits?** No. The largest output is Tailwind's warm engine, 3.9 MB in 222 ms, which is about 17 MB/s on one core and far from any memory or disk limit. Medians grow with the utility count in every tier, as they should when the work grows.
4. **Did it error?** No. The protocol writes no record when any subject errors, times out or falls back, and this record exists. `TEACSS_ENGINE_STRICT=1` was set, every teacss-rs sample loaded `teacss-engine.darwin-arm64.node`, and no teacss-ts sample did.
5. **Does it reproduce?** Each subject has 30 interleaved samples per cell. The median IQR across all 63 groups is 2.1 % of the median. Tailwind's warm engine is the noisiest at 18 % to 23 %. All of these gaps are smaller than the gaps between subjects.
6. **Does it matter?** The build tier is what a user waits on. Its baseline is 258 ms of Vite with no CSS engine. At the largest cell the CSS work adds 561 ms for Tailwind, 1 490 ms for teacss-rs and 3 492 ms for teacss-ts.
7. **Did it even happen?** Yes. All 63 subject, tier and cell groups produced one output hash each. teacss-ts and teacss-rs produced identical bytes in both tiers. `bench verify` on the same corpus confirmed every case's properties and conditions in both tools.

## Findings beyond the headline

- **teacss-ts build time follows the file count.** At 1 000 utilities, teacss-ts takes 2.02x Tailwind's time with 3 files and 6.34x with 300 files. teacss-rs stays between 1.62x and 1.68x across the same cells. The cost appears to be per transformed module on the TypeScript path, which the Rust engine removes. The follow-up profile confirms this: each module's extraction runs a forced snapshot comparison of the whole configuration twice, about 5.6 ms per module, which the Rust path skips.
- **Output size differs by design.** At the largest cell the Tailwind build emits 2.7 MB of CSS (229 KB gzip). TeaCSS emits 1.06 MB (88 KB gzip). Both cover the same cases with the same properties and conditions, but they do not do byte-equal work. The report compares time to a correct stylesheet, not time per byte.

## Limits of this run

- **Load during the run.** The machine started at 13 % one-minute load per core and passed the gate. During the run, the load recorded around each cell was 20 % to 36 %. After the run it was still 4.3 on 12 cores, with node processes from other sessions running. Part of the in-run load came from outside the benchmark. Interleaving spreads that noise across all subjects, and complete separation means it cannot reverse a verdict. It could still hide a small difference, and the 1 000-utility warm comparison is the place where that could matter.
- **Node 26.7.0, not the pinned 24.14.1.** The environment block records Node v26.7.0: the orchestrator was started from a shell whose `node` was a newer Volta install, and every subject process inherits that binary. Spec v01.1 names Node 24. Nothing here is known to depend on the Node version, but it is a deviation, so `bench run` now refuses to start when the running Node differs from `.node-version` unless `--allow-node-mismatch` is passed, and the next run will be on the pinned version.
- **One machine.** These numbers come from an Apple M2 Max (12 cores, macOS). The CI workflow is the cross-check and has not run yet.
- **Engine and core versions differ.** The Rust engine is 0.8.5-alpha.4 and its parity oracle is teacss-ts 0.8.5. TeaCSS core is 0.9.0-alpha.1. Strong equivalence still held on this corpus.
- **The build clock included the harness's own work.** Found after this run ([spec v01.1 revision 4](../specs/v01.1-benchmark-protocol.md)): each build sample ran from spawn to exit, and before exiting the subject process hashed and compressed its output, removed its workspace and read its native modules. At 20 000 utilities that is about 12 ms for TeaCSS's 1 MB stylesheet and 23 ms for Tailwind's 2.8 MB, so Tailwind's build medians here are too high by roughly the difference, and every build's CPU time and peak RSS include it. The rankings at 20 000 utilities do not change; the build ratios are overstated. Later runs end a build sample when the build returns.
