## The seven questions

1. **Why not double?**
   - The warm teacss-rs engine spends 48 % of its profile in the facade's `generate`, which carries the native call.
   - In the Vite build, the warm engine (51 ms) is 21 % of the 245 ms the CSS adds. The top build frames are module compilation (8 %) and `generate` (7 %).
   - In the R1 investigation, teacss-rs located the per-module extraction cost in the scanner's masking passes (`extract_code`).
   - Tailwind's build spends 18 % in lightningcss.
2. **Was it tuned?**
   - Every subject ran its published package with the entry its documentation gives.
   - The `-default` subjects took 0.99x (teacss-rs), 0.98x (teacss-ts) and 1.00x (Tailwind) the tuned build time.
   - The `-postcss`, `-rsbuild` and `-bun` subjects use each tool's own plugin for that pipeline.
   - Every TeaCSS subject ran with `TEACSS_ENGINE_STRICT=1`.
3. **Did it break limits?** No. The largest output is Tailwind's under Bun, 3.2 MB. Medians grow with the utility count in every tier.
4. **Did it error?** No.
   - A run with any error, timeout, fallback, or missing or duplicate native binary writes no record, and this record exists.
   - Every Rust TeaCSS sample loaded `teacss-engine.darwin-arm64.node`, in Node and in Bun. No TypeScript sample did.
5. **Does it reproduce?**
   - Each of the 396 groups has 30 interleaved samples. The median IQR is 3.3 % of the median.
   - The noisiest groups are Tailwind's warm and +10 engine at some cells (21 % to 40 %).
   - The TypeScript engine's dev +100 at 1 000 utilities is next (22 % to 23 %), and so is teacss-rs's engine +100 at 1 000 utilities, around 2 ms (21 % to 22 %).
   - None carries a headline.
6. **Does it matter?**
   - The dev tier is what a user waits on most often. Saving a file now takes 70 ms against Tailwind's 321 ms.
   - At the largest cell, the CSS work adds 245 ms for teacss-rs, 575 ms for Tailwind and 852 ms for teacss-ts to a 235 ms Vite build.
   - In a 1 000-class project Tailwind is ahead by at most 25 ms, and in 7 of the 15 build tables the two cannot be told apart.
7. **Did it even happen?** Yes.
   - Every warm and build group produced one hash.
   - The build hashes are the same as in 0.9.0: `ee274f23…ef007` at 1 000 x 300 and `f4ea28ce…a96d4` at 20 000 x 300.
   - teacss-ts and teacss-rs produced byte-identical output in all 3 510 sample pairs across the five groups: 1 890 main, 810 default-config, and 270 each in postcss, rsbuild and bun.

## Against the third official report (0.9.0, 2026-10-23)

The protocol, machine and Node are the same, so every tier is comparable. The output is byte-identical to 0.9.0. 0.9.1 carries four changes, each of which was measured on its own beforehand in the unreleased lane ([optimization cards](../knowledge/optimization-cards-2026-10-24.md)):

- T1 (teacss-ts #933): by default the dev server keeps Vite's PostCSS fast path for the generated sheet;
- T3 (teacss-ts #929): a faster font-URL rewrite;
- R2 (teacss-rs #467): dev rounds no longer copy every token across NAPI;
- F13.11 (teacss-rs #468): a faster memo hit, which no measured scenario takes.

At 20 000 x 300:

| --- | --- | --- | --- | --- |
| Dev +10 | teacss-rs | 100.4 ms | 70.1 ms | -30.3 ms |
| Dev +10 | teacss-ts | 260.6 ms | 227.8 ms | -32.8 ms |
| Dev +10 | Tailwind | 322.5 ms | 320.6 ms | -1.9 ms |

| Engine, warm | teacss-rs | 51.8 ms | 51.3 ms | -0.5 ms |
| Engine, +10 | teacss-rs | 16.7 ms | 17.1 ms | +0.4 ms |

- **Dev tier.**
  - teacss-rs's dev +10 fell by 30 ms. The unreleased lane measured -25 ms for T1 and -5 ms for R2, which add up.
  - T1's own target was 70 ms or less. T1 alone reached 77.7 ms, and 0.9.1 with R2 reaches 70.1 ms.
  - Tailwind did not move.
- **Build tier.**
  - teacss-rs's Vite build fell by 12 ms, in line with T3's -13.5 ms. Tailwind's Vite build rose by 18 ms, and the other build tools' Tailwind and TeaCSS builds rose by 5 ms to 24 ms. That fits a machine running about 2 % slower than on the day of the third report.
  - The PostCSS, Rsbuild and Bun teacss-rs builds rose by 6 ms to 8 ms, within that drift: T3 changes the Vite plugin's rewrite.
- **Engine tier.** No change, as the unreleased lane found.

## Limits of this run

- **One machine:** an Apple M2 Max with 12 cores, running macOS. The Linux cross-check has not run.
- **One corpus.** The community corpus still waits for the owner's repository list, so every number here comes from the generated paired corpus.
- **The Bun group** runs in the Bun runtime. Its baseline and absolute times compare runtimes as well as CSS tools; the deltas over its own baseline are the comparison.
- **The author of this benchmark also develops TeaCSS.** The method, the pair table and the raw samples are published, and the run is reproducible from a clean clone.

## Later protocol change

Spec v01.1 revision 5 and v02.1 revision 5 (2026-10-24, after this run) give every Node build and dev subject Node's compile cache, as the `vite` and `rsbuild` CLIs enable it. This run and the earlier reports ran every subject without the cache. That was the same for every tool, so it is not a bias, but build and dev numbers from revision 4 and revision 5 are not comparable. The change came first because teacss-ts's B5 enables the cache from inside the TeaCSS plugin. Under revision 4 that would have given only TeaCSS the cache, and also sped up the bundler in its builds. B5 is in no published package and in no report.
